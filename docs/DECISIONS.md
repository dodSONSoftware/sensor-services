# Sensor Services — Engineering Decisions

This document records important engineering tradeoffs apparent in the current codebase. These are documented implementation decisions, not claims of external approval or historical ADR discussions.

| Decision | Rationale / benefit | Consequence / reconsider when |
| --- | --- | --- |
| One Express process with explicit route registration | Central composition, predictable middleware order and startup assertions | Route classes must be explicitly registered; add metadata and drift coverage for new endpoints |
| Separate sensor command API from telemetry ingestion | Keeps control requests independent from metric ingestion | Telemetry retrieval belongs in sensor-telemetry; do not add parallel ingestion here |
| MQTT V3 envelopes with command IDs and bounded wait | Correlates asynchronous replies with originating HTTP requests | Maintain firmware compatibility; keep disconnect/timeout/serialization paths tested |
| Strict Zod configuration schema | Fail fast on typos and runtime-incompatible values | New configuration keys require schema, docs and tests |
| Single YAML config including credentials | One operational source of truth for runtime and config API | Trusted LAN and filesystem security are mandatory; not appropriate for untrusted exposure without auth |
| Atomic full-document config writes | Prevent torn writes and preserve existing mode | Updates must supply full document; concurrent external edits need operational coordination |
| Hot-reload log level only | Avoid partial reconfiguration of long-lived clients and unintended Loki destination changes | Most edits require restart |
| PostgreSQL-backed settings with in-memory fallback | UI remains functional during DB downtime | Fallback updates are non-durable; DB write errors after successful init must not be falsely accepted |
| Route declaration/live-router drift checks | Fail startup if endpoint metadata diverges | All new routes require declarations and help metadata |
| Separate Prometheus API registry and bounded route labels | Scraping remains low-cardinality and independent of sensor ingestion | Exclude `/health` and `/metrics` from rate limiting |
| Explicit, ordered and bounded shutdown, with the HTTP close step capped by a short grace + `closeAllConnections()` and the settings-pool close capped by a short `pool.end()` race (~4s) | Avoids stuck resources and forced Docker termination; a slow in-flight request, the Node 22 keep-alive idle drain, or an in-flight settings query on a slow/hung database (pg-pool's `end()` waits for every checked-out client and has no forced-terminate API; the query could otherwise be held to the 30s `statement_timeout`) can no longer consume the whole 15s budget or turn a clean stop into exit 1 | Docker stop grace must exceed the 15-second application deadline; in-flight HTTP requests are torn down after the grace (~4s) rather than completing up to their own cap — acceptable at shutdown; when the pool-close bound wins, the pending close is abandoned with a warning — the process exits immediately, so the OS reclaims the abandoned socket |
| Swagger scans route source at runtime | Automatically derives API documentation from existing route definitions | Runtime image must retain the source route directory |
| Central two-tier log redaction at the `Logger` `write_*` seam (shared library) | One auditable pass covers every current/future caller, including untrusted forwarded sensor log lines; caller-side redaction kept as defense in depth (the write-config metadata projection is stronger than masking) | Hot path: one linear key-pattern pass plus up to two literal substring passes per line; the key tier recognizes key/value forms only (free-form prose with unknown values relies on the value tier and caller-side redaction); the `dodsonlabs/` change must be mirrored to sibling services; re-verify the value tier if config secrets ever hot-reload (values are captured at construction; only `log-level` hot-reloads today) |
| Restart token as an environment variable and the enable switch (no separate flag) | `/api/read-config` returns config unredacted, so a config.yml key would expose the token over HTTP; one strict validity rule is easier to operate and audit than a flag plus a token; "disabled, not open" removes the unauthenticated surface from every unset-token deployment | A set-but-invalid token disables the endpoint and warns at startup — it deliberately never refuses startup, which would crash-loop the whole service over one optional endpoint; the ASCII-only charset keeps validity checkable with one regex (character count = byte count) |
| Restart implemented as self-SIGTERM plus the Docker restart policy | The container has no Docker socket/CLI/SDK and runs non-root, so it cannot talk to the Docker daemon; self-signaling SIGTERM needs none of that and reuses the one tested graceful path shared with `docker stop` (MQTT disconnect, bounded HTTP drain, logger flush, exit-code ownership) instead of a second, divergent restart mechanism | `202` is best-effort (the process may exit before the client finishes reading); the caller must verify the new process via `/health`; the container must actually have a restart policy (`unless-stopped`) or the service does not come back; a leaked token permits repeated-restart DoS, so exposure stays LAN-only with a strong token |
| Short-TTL (~5 s, hard-coded) dependency-probe cache shared by `/health` and `/about` (single-flight; negative results cached) | `/health` is rate-limit-exempt, so an unthrottled client could otherwise fire a full bounded probe per request — and a *dead* dependency is the worst case, because every request re-runs the full 2.5 s probe | Health status lags real dependency recovery by up to ~5 s (acceptable for orchestration semantics; degradation is still detected within one TTL window); the 2.5 s probe bound (vs Docker's 5 s healthcheck deadline) is unchanged; the TTL is deliberately not a config key (it tunes against two other fixed values and a key would mean schema + docs + reload policy + boundary tests for zero operational benefit) |
| Explicit 64 KiB inbound payload length guard in `MqttNetworking.on_message()`, applied before topic tracking and `JSON.parse` | The broker is unauthenticated and mqtt.js 5.x imposes no client-side limit on RECEIVED payloads (the v4 `maxPayload` option is outbound-only and silently ignored in v5), so a forged oversized `iot/v3/log` payload would otherwise pass `JSON.parse` and be stringified (2x memory) into the logger | Messages >64 KiB on ANY topic are dropped with a warning (largest legitimate document ~4 KB, so ~16x headroom); the guard deliberately never logs payload content; an oversized payload on an untracked topic now logs the size warning instead of the untracked-topic warning (strictly more informative); no ack changes needed (QoS 0 subscriptions, v5 PUBACKs after the synchronous handler). The `dodsonlabs/` change is a local deviation: it must be mirrored to sibling services and must not be silently dropped during upstream sync |

When changing an architectural decision, update this file with the new behavior, motivation, risks and migration/testing implications; avoid preserving historical claims unsupported by repository evidence.
