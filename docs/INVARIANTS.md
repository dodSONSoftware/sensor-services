# Sensor Services — System Invariants

This document lists properties that must remain true after changes. Relevant tests and implementation modules are the enforcement points.

1. **Startup validation:** strict `configSchema` rejects unknown, missing or invalid settings before listener startup; values accepted by Zod must also be accepted by their downstream consumers (`schemas/configBoundary.test.ts`).
2. **Credential hygiene:** configuration/log payloads must be sanitized before logging; `db-password`, `loki-url`, `ip-pinger-config-token` and recursively recognized secret keys must not leak through logs. Every log line passes a central two-tier redaction in the shared `Logger` (this service's own secret values by exact value; recognized sensitive keys by key/value pattern) before reaching any transport, with caller-side sanitization (`redactConfig`, `redactSecrets`, write-config metadata projection) retained as defense in depth. Raw configuration API reads are sensitive and must remain within trusted access controls.
3. **Middleware order:** request correlation and metrics execute before CORS/rate limiting; rate limiting precedes JSON body processing; `/health` and `/metrics` cannot be rate-limited.
4. **Request correlation:** `X-Request-ID` exists on handled requests and propagates to async request log context. A client-supplied ID is reused only when it is a single non-empty string of at most 128 characters; absent, multi-valued (array), or oversize values are replaced with a generated UUID so the ID always stays a bounded single string (it is echoed in the response header and interpolated into every log-line tag).
5. **Routes:** every route creator requires explicit `register()`; each live route must match module `__routes` and `__routesHelp` metadata on startup. Unmatched paths remain 404 and are logged at warn severity.
6. **MQTT correlation:** publish only with valid V3 envelopes; accept responses for the active `command_id` only. Each same-type command owns its slot and response snapshot; do not reuse results across callers.
7. **MQTT failure handling:** reject disconnected/unpublishable commands as 503 and always release claimed slots. Do not queue a QoS-0 command and claim it succeeded when the broker disconnected.
8. **Command timeout:** `command-silence-timeout-ms` cannot exceed 10 seconds; each HTTP command wait also has a hard 10-second cap. A cap hit by the active command's own wait is a real fault and logs at error; a cap hit by a queued slot waiter is routine and logs at debug (it simply retries the claim).
9. **Sensor writes:** `/sensors/write-config/:source` must target a concrete sensor; reject literal/encoded/whitespace broadcast `*` before publishing. Broadcast reads and reboots remain supported.
10. **Config consistency:** `read-config` reflects validated disk state and `read-running-config` reflects current memory state. Writes replace the full document atomically and preserve the file's existing mode. Only log-level hot-reloads.
11. **Settings semantics:** PostgreSQL initialization only becomes available after full success. Without a pool, settings changes persist **in memory only** and report `X-Settings-Persisted: false`; after pool initialization, a failed write does **not** mutate the cache and reports an error.
12. **Settings updates:** unknown keys reject the entire patch (400); no partial mutation on schema error.
13. **Pinger analysis:** validate pinger config before analysis; unreachable/invalid pinger data degrades without mutating live sensor input. A pinger config API that rejects the token (401) or reports itself disabled (503) degrades with a warning that names the cause, not a generic "service unavailable". Validate target addresses to prevent outbound URL manipulation.
14. **Log access:** source, level and query limit are validated/bounded to avoid LogQL injection or excessive results.
15. **Health and shutdown:** dependency probes are bounded and concurrent; degraded health is not automatically HTTP 503. Shutdown is re-entrant safe and bounded to 15 seconds, closes resources in order and preserves success (signals) vs fatal (nonzero) exit semantics. The final exit code is the WORST requested across all shutdown entries (tracked state, monotonic escalation), not the first caller's parameter: a fatal fault (`uncaughtException` / `unhandledRejection`) that lands while a clean stop is already in flight is absorbed by the re-entrancy guard (the sequence never re-runs) but still exits 1 — a fault can never be masked into a clean-stop 0. The HTTP close step is itself bounded: after a short grace (~4s) all connections — in-flight and idle keep-alive — are force-closed, so a slow in-flight request or the keep-alive idle drain can never consume the whole budget and starve the MQTT / settings / logger closes.
16. **Container lifecycle:** mounted YAML takes precedence over compiled fallback; runtime is non-root; Docker's 20-second stop grace exceeds the app's hard shutdown timeout.
17. **Restart endpoint fail-closed:** `POST /restart-service` is enabled only when a valid `RESTART_SERVICE_TOKEN` (32+ alphanumerics) AND an injected shutdown hook are both present; missing either half answers the byte-identical 503 (no config probing). Unset, empty, or invalid tokens disable the endpoint and never refuse startup. The token is an environment variable only — never a `config.yml` key (the config API returns config unredacted) — and is never logged in any state; it is a distinct secret from `ip-pinger-config-token`. Non-POST verbs get 405 (`Allow: POST`) before authentication. Authentication requires exactly one `Authorization` header (duplicates detected via `rawHeaders`, rejected before any comparison), the exact shape `Bearer <token>` (case-sensitive scheme, no embedded whitespace), and a constant-time compare with a length pre-check; failures get 401 + `WWW-Authenticate: Bearer` and an audit carrying the socket address but never the header value. The lifecycle callback fires exactly once (single-flight: the guard is set synchronously before the 202 is written, released only if the callback throws) and only after the 202 is delivered (a bounded fallback timer covers a vanished client); the 202 carries `Connection: close` and every response `Cache-Control: no-store`. The HTTP layer never touches `process`: the hook self-signals SIGTERM (the same graceful path as `docker stop`), and a racing clean signal is absorbed by the shutdown re-entrancy guard (which never re-runs the sequence; a racing FATAL entry still escalates the final exit code, see #15). The request stream is never consumed (the JSON parser skips the path), so a malformed/truncated body cannot 400 before the token gate or emit on an unread stream.

Use `npm run blt` and scenario-specific tests before accepting changes to these guarantees. Some operational properties additionally require `tests/docker/verify.sh` and running services.
