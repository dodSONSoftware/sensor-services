# Changelog

All notable changes to the sensor-services project are documented here. Versions are listed newest first.

## [4.17.12] — Onyx Falcon (2026-10-18)

- `GET /sensors/logs/:source` now answers **503 Service Unavailable** (with the same `Loki logging not configured` body) instead of 500 when Loki is unconfigured (`loki-url` absent or `loki-enabled: false`). An unconfigured Loki endpoint is a deployment-normal, schema-legal state (both keys are optional, no fail-fast at startup), so 500 was misclassifying a steady-state condition as a server fault for alerting; 503 matches the service's own dependency-unavailability convention (MQTT broker outages already answer 503). Observable API change for Loki-less deployments: callers that keyed on 500 for this case should now expect 503. Genuine failures with Loki configured (unreachable upstream, non-OK API response) still answer 500. Swagger documents the 503.
- Out-of-range decimal nanosecond timestamps in a Loki response no longer 500 the whole request. A 40+ digit `values` timestamp passes the `/^\d+$/` format guard but lands outside the `Date` range after the ns→ms division, so `toISOString()` threw `RangeError` and the catch-all discarded every valid entry in the response. The offending entry is now skipped with a non-leaking warning (entry content is not logged) and the sibling streams are returned as usual.
- Docker images now build from the committed lockfile: both stages use `npm ci` (builder) and `npm ci --omit=dev` (runtime, replacing the deprecated `--only=production` alias). Previously the builder's `npm install` could rewrite `package-lock.json` and stage 2 installed from that mutated lock — a latent drift/supply-chain gap against the repo's own `npm ci` quick-check. `npm ci` fails fast on any lock/package mismatch, which is the point. Verified end-to-end by `tests/docker/verify.sh`.
- A rejecting `/health` dependency probe can no longer take the process down: `probeDependencyHealth` now stores `probe().catch(() => false)`, so a probe that rejects (a contract the current two probes honor, but a future probe could break) degrades to "unreachable" and is cached like any negative result. Previously the rejection would reach the process-level `unhandledRejection` handler through the shared in-flight promise and the health route handler, triggering an exit-1 shutdown from the health endpoint. New tests pin reject→false, caching, single-flight across concurrent callers, and reset.
- The settings-store bootstrap path (`settingsStore.init()` / `runInitQueries()`) now logs through the central logger instead of raw `console.*`, so its messages pass the central two-tier redaction seam like every other log line. This supersedes the 4.17.6 note that the startup-path `console.*` sites were "explicitly tolerated": parameter-based connections mean pg errors cannot embed a connection string today, but the consistency gap is closed and the seam will protect automatically if that ever changes. No response behavior changes.
- Documented the 429 metric-attribution limitation (by design): the rate limiter answers before Express routing sets `req.route`, so 429 responses are counted under `http_requests_total{route="unmatched"}` alongside 404s; per-route 429 attribution is unavailable — dashboards should slice by `status="429"`. Moving the limiter after routing would break the middleware-ordering invariant and the "a 429'd request's body is never parsed" property, so this is accepted and recorded in KNOWN_ISSUES.md with a pointer from ARCHITECTURE.md.

## [4.17.10] — Onyx Falcon (2026-10-18)

- Fixed a shutdown-boundary hole: `settingsStore.shutdown()` awaited pg-pool's `end()` with no bound, but `end()` only resolves once every checked-out client has been released — so an in-flight `PATCH /ui/settings-update` on a slow or unreachable database (an in-flight query is held to the pool's 30s `statement_timeout`) could hold the shutdown sequence past the 15s hard net (the ~4s HTTP drain grace plus the 5s MQTT close leave at most ~6s for this step), forcing `process.exit(1)` on a clean, operator-requested stop and inverting the documented success-vs-fatal exit semantics (INVARIANTS #15). `pool.end()` is now raced against a 4s bound (worst-case total 4 + 5 + 4 = 13s stays under the net); when the bound wins, the pending close is abandoned with a warning through the logger — pg-pool has no forced-terminate API, and the process exits immediately after this step, so the OS reclaims the abandoned socket. The healthy path is unchanged: a live database's `end()` wins the race instantly and logs nothing. A late settle or reject of the abandoned `end()` is observed by handlers attached at race time, so it can never surface as an unhandled promise rejection after the logger has closed. Regression tests pin the behavior with a fake pool whose `end()` never resolves (a client checked out on a hung query): `shutdown()` resolves exactly when its bound fires and warns once, and the same test hangs to the jest timeout against the pre-fix code.

## [4.17.9] — Onyx Falcon (2026-10-18)

- Every 200 sensor command response (`/sensors/get-details`, `/sensors/reboot`, `/sensors/read-config`, `/sensors/write-config`) now carries an `X-Command-Truncated` header: `true` when the active command's 10-second hard cap expired before its wait completed (the result array is only what arrived within the cap and may be partial), `false` when it completed in time. Previously a capped response was byte-identical to a complete one — the cap was documented only in terms of server-side log severity (INVARIANTS #8), never the response — so a caller with no fleet-size knowledge could render a partial result set as the whole fleet. The header follows the existing `X-Settings-Persisted` idiom (always present, stringified boolean) and is visible on both the raw and the `command_metadata`-enriched (reboot) response shapes. A queued slot waiter's cap hit never flags the response: that wait only delays the claim and never publishes a command, so the active command's own wait alone determines completeness. Tests pin all three cases (capped → `true`, queue-waiter cap → `false`, normal completion → `false`); swagger, `__routesHelp`, and INVARIANTS #8 document the contract.

## [4.17.8] — Onyx Falcon (2026-10-18)

- Inbound MQTT payloads are now length-guarded before any processing: `MqttNetworking.on_message()` drops any PUBLISH payload over 64 KiB with a warning that deliberately excludes payload content, applied before topic tracking and `JSON.parse`. The broker is unauthenticated and mqtt.js 5.x imposes no client-side limit on RECEIVED payloads (the v4 `maxPayload` option is outbound-only and silently ignored in v5), so with `forward-sensor-logs` on by default a forged oversized `iot/v3/log` payload would previously have passed `JSON.parse` and been stringified (2× memory) straight into the logger. The largest legitimate document is ~4 KB, so the limit carries ~16× headroom, and the guard covers any topic, not just the log topic. No ack semantics change: subscriptions are QoS 0 and v5 emits the QoS-1 PUBACK after the synchronous handler, so dropping cannot cause a broker redelivery loop. One deliberate side effect: an oversized payload on an untracked topic now logs the size warning instead of the untracked-topic warning (strictly more informative). Note: this is a local deviation in the separately maintained `code/src/dodsonlabs/` shared library — it must be mirrored to sibling services and must not be silently dropped during upstream sync (recorded in DECISIONS.md and KNOWN_ISSUES.md).

## [4.17.7] — Onyx Falcon (2026-10-18)

- Fixed a probe-amplification hole on `GET /health`: every request — and `/health` is rate-limit-exempt — fired two fresh bounded 2.5-second probes at the IP-pinger and sensor-telemetry `/health` endpoints with no caching, so an unthrottled client could amplify downstream load up to 2× request QPS, worst when a dependency was down, where every request re-ran the full 2.5 s probe. Dependency probe results are now served from a short-TTL (~5 s, hard-coded) cache shared by `/health` and `/about`: single-flight (concurrent callers share the in-flight probe), keyed by probe URL, and **negative results are cached identically**, so a dead dependency can no longer amplify probes. The 2.5 s per-probe bound (vs Docker's 5 s healthcheck deadline) and the HTTP contract are unchanged; `timestamp`/`uptime_seconds` remain per-request. Health status can now lag real dependency recovery by up to ~5 s (degradation is still detected within one TTL window). The TTL is deliberately not a config key.

## [4.17.6] — Onyx Falcon (2026-10-18)

- Fixed the settings-patch warnings on the request path (`PATCH /ui/settings-update` → `settingsStore.doPatchSettings`) to route through the central logger instead of raw `console.warn`. The two warnings — update applied in memory only (no active pool) and persistence failure (changes discarded) — bypassed all three logging guarantees: they never reached the Loki transport, never passed the central two-tier secret redaction seam (a raw `pg` driver error can embed connection-string details in its message), and carried no request ID. They now emit through `logger()?.write_warn` with the same null-safe convention as every other request-path call site — deliberately no console fallback, which would recreate the bypass. The six startup-path `console.*` sites in `init()` are untouched (bootstrap context, explicitly tolerated). Response behavior is unchanged (500 body, `X-Settings-Persisted` header). Tests pin both paths: the warning goes to the logger and never to `console.warn`, including the no-logger-configured case.

## [4.17.5] — Onyx Falcon (2026-10-18)

- Added regression coverage pinning the hand-maintained `GET /endpoints` discovery list to the union of all seven modules' declared `__routes` arrays — set equality in both drift directions (a new route missing from the list, and a stale list entry with no backing route) plus a duplicate-entry check. The other two route-metadata surfaces (`__routes` ↔ `__routesHelp` per module, and registered-vs-declared on the live router) were already covered by the P3-4 drift tests and the startup `assertRoutesMatchDeclared` assertion; `/endpoints` was the one surface where adding a route would silently serve stale endpoint documentation. Test-only change: no production code touched.

## [4.17.4] — Onyx Falcon (2026-10-18)

- Extracted the 10-second HTTP command hard cap into a single shared constant (`HTTP_COMMAND_HARD_CAP_MS` in `code/src/common/constants.ts`), now referenced by both the `command-silence-timeout-ms` config bound (Zod `.max`) and the sensor command wait (`__max_wait_ms` in `sensorController.ts`). The two inlined `10_000` literals that had to be kept in sync by comment can no longer drift. Pure refactor: behavior and the startup validation message are byte-identical, and the schema boundary tests now pin to the constant instead of a third copy of the number.

## [4.17.3] — Onyx Falcon (2026-10-17)

- Fixed `POST /restart-service` so a malformed or truncated request body no longer 400s in the JSON parser before the token gate. The endpoint's contract is that the request stream is never consumed (the body is irrelevant), but the parser was told to skip the path via body-parser's `skip` option — which the pinned body-parser (1.20, and no 1.x or 2.x release) silently ignores — so a bad body 400'd in every token state, leaking which half a deployment had and breaking the byte-identical fail-closed responses. The parser now runs behind a thin wrapper that invokes it conditionally, and the exclusion covers every routing of the path, not just the bare form: Express's default (non-strict) routing also serves `/restart-service/`, and the wrapper sees `req.path` verbatim with the trailing slash intact — anchored with the same `/?` pattern as the rate-limit exemption above, so it cannot leak to `/restart-servicex` or deeper paths. Every other request runs the exact same parser as before. Regression tests install the real middleware plus the real restart routes (the full production pipeline, which the route-level suite skips) and pin, for both routings: disabled → the byte-identical 503, no Authorization → 401 + `WWW-Authenticate: Bearer`, valid token → 202 with the hook firing exactly once, all from a malformed body.

## [4.17.2] — Onyx Falcon (2026-10-17)

- Fixed the log-pagination cursor (`end`) on `GET /sensors/logs/:source` so a malformed value is rejected instead of silently ignored. When `end` was present but unparseable (e.g. `?end=not-a-date`, a truncated ISO string, or repeated `?end=` parameters, which stringify to `"a,b"`), `Date.parse` returned NaN and the handler silently treated the cursor as absent — it queried the fresh 1-hour newest-first window instead of the requested historical one, with no 400 and no warning in the response. A client paginating history by feeding the previous page's oldest timestamp back as `end` would, on any cursor malformation, silently re-fetch the newest page forever and never reach the older entries, which reads as "old logs are gone." A present-but-unparseable `end` now answers `400` (`invalid end timestamp; expected ISO 8601`) before the Loki fetch, mirroring the handler's existing invalid-`level` 400; valid ISO 8601 `end` values (2-hour pagination window) and an absent `end` (fresh window) are unchanged. Regression tests: invalid and repeated `end` → 400 with the Loki fetch never called, and a valid `end` still reaches the Loki query with the exact requested window.

## [4.17.1] — Onyx Falcon (2026-10-17)

- Fixed the process exit code when a fatal fault landed while a graceful shutdown was already in flight. `shutdown()` is guarded by a single re-entrancy boolean, and the exit code was fixed by whichever caller started the sequence — so a `uncaughtException` or `unhandledRejection` arriving inside the (up to 15-second) shutdown window after a `SIGTERM` was logged, then absorbed by the guard, and the process exited 0, a clean stop, despite a recorded fatal fault. Supervisors and containers saw a clean stop (the fault was visible only in logs), and an `on-failure`-based deployment lost its restart signal entirely. The final exit code is now tracked state — the worst code requested across all `shutdown()` entries — escalated before the guard, so a clean stop that starts first still owns the exit (the sequence never re-runs, the logger still closes exactly once), but a fatal request that arrives second raises it to 1 and the process exits nonzero. Every other ordering is behavior-preserving: fatal-first still exits 1, duplicate clean stops still exit 0, and the 15-second hard-shutdown net still forces exit 1. The policy is extracted to `escalateExitCode()` in `common/shutdown.ts` (where the other shutdown primitives live) for testability.

- Added regression tests for the escalation: unit tests on the extracted policy (clean/clean stays 0, clean-then-fatal becomes 1, fatal-then-clean stays 1, fatal/fatal stays 1) and source pins that the fatal handlers' codes flow through the tracked escalation rather than straight to `process.exit()` with the first caller's parameter; documented the worst-requested-code semantics in `docs/INVARIANTS.md` (invariants 15 and 17).

## [4.17.0] — Onyx Falcon (2026-10-17)

- Added an optional, fail-closed `POST /restart-service` endpoint that schedules a graceful self-restart. The endpoint is armed only by a `RESTART_SERVICE_TOKEN` environment variable (32+ alphanumeric characters; `openssl rand -hex 32` generates one) combined with the shutdown hook `index.ts` injects at startup — missing either half answers the byte-identical `503` so a client cannot probe which one a deployment lacks, and unset, empty, or set-but-invalid tokens simply leave the endpoint disabled while the service boots and runs normally (a bad token can only ever move it *off*, never crash startup). The token is an environment variable deliberately rather than a `config.yml` key — `/api/read-config` returns the configuration unredacted, so a config key would expose it over HTTP — and it is a distinct secret from `ip-pinger-config-token` (neither is ever accepted in the other's place). Authenticated requests use `Authorization: Bearer <token>` with an exact header shape (duplicate headers detected via `rawHeaders` and rejected before any comparison, case-sensitive scheme, no embedded whitespace) and a constant-time compare with a length pre-check; failures get `401` + `WWW-Authenticate: Bearer`, non-POST verbs get `405` with `Allow: POST` before authentication, and a duplicate request while a restart is pending gets `409`. On acceptance the service answers `202` (`restart_scheduled`) fully first — with `Cache-Control: no-store` on every response and `Connection: close` on the `202` — then runs the same graceful SIGTERM shutdown an operator `docker stop` triggers (the process self-signals; the HTTP layer never touches `process`), and the container's `restart: unless-stopped` policy starts it again with its persisted configuration. The lifecycle callback fires exactly once after the response is delivered (a bounded 2-second fallback timer honors an accepted restart even if the client disconnects first, and a throwing callback releases the single-flight guard so a later request can retry), and the request stream is never consumed — the JSON parser skips this path — so a malformed or truncated body cannot wedge the handler. The token value never reaches any log line in any state; audits carry only the observed socket address. `docker-compose.yml` injects `RESTART_SERVICE_TOKEN=${RESTART_SERVICE_TOKEN:-}` (an unset host variable arrives empty — the deployed "disabled" state), and `code/.env.example` is the git-ignored `.env` template. A restart re-reads the persisted `config.yml` but does not rebuild the image, update deployment files, or reconcile a changed `express-port` (compose port map, `EXPOSE` and `HEALTHCHECK` are pinned to 32000), a container an operator stopped stays stopped, and a leaked token permits repeated-restart denial-of-service — so exposure stays LAN-only with a strong token.

- Added regression tests covering all four enablement states (valid/empty/invalid token × hook present/absent, including byte-identity of the disabled `503` across the two fail-closed halves), the Bearer auth rules (shape, duplicates, comma-joined values, wrong value/length, distinct-secret rejection), the single-flight and response-before-shutdown guarantees (sequential + concurrent, client-disconnect fallback, callback-failure guard release), the token-never-logged discipline, source pins that the restart hook self-signals SIGTERM with no direct `process.exit`, and an end-to-end integration test (compiled app: `202` followed by a clean exit 0); updated the route-drift, Swagger, and endpoint-table regression suites, and documented the endpoint and token in `docs/ARCHITECTURE.md`, `docs/CONFIGURATION.md`, `docs/INVARIANTS.md`, `docs/KNOWN_ISSUES.md`, `docs/DECISIONS.md`, and the README endpoint table.

## [4.16.0] — Quartz Falcon (2026-10-17)

- Added an optional `ip-pinger-config-token` configuration key so that `GET /sensors/ippinger-analyze` can keep fetching the pinger's configuration when the ip-pinger service has its configuration API protected by a token. The service calls the pinger's config endpoint (`GET /read-config`) on every `/sensors/ippinger-analyze` request, but previously never sent the `x-config-token` request header — so in a deployment that enabled the pinger's config API, every analyze call 401'd and the endpoint silently degraded to a live-sensors-only partial result with a generic "service unavailable" warning, making it look like the pinger was down. With `ip-pinger-config-token` set, its value is now sent as the `x-config-token` header on that fetch (and omitted when unset, so deployments that don't use the pinger's config API are unaffected). The key is optional, must be 32+ alphanumeric characters (the pinger's own token-validity rule, enforced at the config boundary so a mistyped token fails fast at startup instead of at request time), is treated as a secret everywhere other config secrets are (`redactConfig` masking in the startup dump and config API responses, plus the shared Logger's value-tier redaction on every log line), takes effect on restart, and is validated at startup. The analyze endpoint's degraded-mode warning can now also distinguish a 401 (token rejected or missing) from a 503 (pinger's config API disabled), so an operator sees the actual cause instead of a generic "service unavailable" message.

- Added regression tests covering the new config key's schema acceptance/rejection, its redaction, the header's presence when configured and absence when not, and the 401/503 degraded warnings; documented the key in `docs/CONFIGURATION.md`, `docs/ARCHITECTURE.md`, `docs/INVARIANTS.md`, the write-config Swagger body, and the `config.yml` example.

## [4.15.1] — Ceramic Falcon (2026-10-17)

- Validated the client-supplied `X-Request-ID` before reusing it. The request-ID middleware previously accepted whatever value arrived and used it verbatim — echoed in the response header and interpolated into every log-line tag for the request's lifetime — so a single unbounded header (up to Node's ~16 KB header limit) of client-controlled text was duplicated into the logs on every request, and the type-level multi-valued (array) case was carried unvalidated into the AsyncLocalStorage store that every downstream consumer types as `string`. The ID is now reused only when it is a single non-empty string of at most 128 characters; absent, multi-valued, empty, or oversize values are replaced with a generated UUID, so the ID is always a bounded single string. The reuse contract for well-behaved clients is unchanged (invariant 4 documents the tightened condition). Covered by new middleware regression tests: reuse, duplicate-header handling, the 128/129 length boundary, the empty-string case, and a direct unit test for the array case, which cannot be reached through the real HTTP stack because Node's parser joins duplicate request headers into one string before any handler runs.

## [4.15.0] — Ceramic Falcon (2026-10-17)

- Added a `release` field to the `/about` response, reporting the release codename alongside the version. The codename was already computed by the service (`APP_NAME` in `version.ts`) and held in the static about info, but `/about` never exposed it — there was no runtime way to see which release a deployment runs other than inferring it from the version number. The field now appears in the `about` object immediately after `version` (e.g. `"release": "Ceramic Falcon"`), is documented in the `/about` Swagger schema, and is covered by a regression test that asserts the field equals the codename constant in `version.ts`, so the assertion tracks the codename through future version bumps.

## [4.14.7] — Silicon Falcon (2026-10-17)

- Documented the reverse-proxy caveat for the rate limiter in `CONFIGURATION.md`. The limiter keys each client by `req.ip` (the express-rate-limit default) and the service does not configure Express's trust-proxy setting: the current deployment exposes the container port directly, so every client has its own source address and its own `rate-limit-max` budget per window. A reverse proxy in front of the service would collapse all clients onto the proxy's source address and give the entire service a single shared budget, so trust proxy (and the limiter's client-key resolution, e.g. an `X-Forwarded-For`-based key) must be configured before one is introduced — or `rate-limit-max` raised to account for the shared addressing. Documentation-only change — no behavior change; the direct-port deployment is unaffected.

## [4.14.6] — Silicon Falcon (2026-10-17)

- Fixed the rate-limiter exemption for the observability endpoints so it holds for every routing of the path, not just the bare form. `/health` and `/metrics` were exempted by an exact `req.path` match, but Express's default (non-strict) routing also serves `/health/` and `/metrics/`, and the rate limiter reads `req.path` verbatim — so a scraper hitting the trailing-slash form was ratable and, once the limit was exhausted, would be 429'd. That could take the container into "unhealthy" (health) or drop Prometheus data (metrics) under load, defeating the documented invariant that these endpoints are never rate-limited. The exemption now matches the bare path plus an optional single trailing slash (`/health`, `/health/`, `/metrics`, `/metrics/`) and nothing else, so it cannot leak to a sibling route. Regression tests cover both trailing-slash routings.

## [4.14.5] — Silicon Falcon (2026-10-17)

- Stopped queue-waiter hard-cap timeouts from logging at error level. `mqtt_command_wait_for_command_completion` — used both by the active command and by queued waiters — logged "Command timed out after 10000ms hard cap" at error severity whenever the 10s hard cap tripped. A queued waiter (a second request of the same command type waiting for the in-flight one) hitting the cap is routine on a busy net: it simply loops and retries the slot claim, yet each retry window emitted a false error-level alert. The cap is now logged per caller: the active command's own wait (its command genuinely did not complete within the cap) still logs at error with the same message, while queue waiters log at debug, naming the command. Logging severity only — no change to command, slot, or response behavior.

The comment, the `swagger-server-url` schema documentation, the `config.yml` example, `CONFIGURATION.md`, and a new `KNOWN_ISSUES.md` entry now state accurately that only loopback is skipped and that `swagger-server-url` should be set for container deployments. ## [4.14.3] — Silicon Falcon (2026-10-17)

- Reworded the settings store's degraded-mode patch warning, which previously logged "[settingsStore] Patch attempted before init() — storing in memory only." on every settings save while PostgreSQL is down — misattributing the cause, since in the intended degraded startup path `init()` did run and simply found the database unavailable (the service continues by design with in-memory defaults). The message now states the actual condition: settings persistence is unavailable (no active pool) and the update was applied in memory only (non-durable, `X-Settings-Persisted: false`), so an operator is no longer pointed at a startup-ordering bug that doesn't exist while the real signal (database down) is buried. Logging hygiene only — no behavioral change.

## [4.14.2] — Silicon Falcon (2026-10-17)

- Fixed `mqtt_*` settings keys (`mqtt_broker_address`, `mqtt_topic_telemetry`, `mqtt_topic_command`, `mqtt_topic_command_response`) being accepted by `PATCH /ui/settings-update` and reported as persisted (`X-Settings-Persisted: true`) while the settings store silently dropped them: the store's known-key predicate validates against `DEFAULT_SETTINGS` membership, and those four keys were absent from it, so the update was skipped with no error — a false success that lost the caller's data. The keys now carry empty-string defaults (matching the `default: ""` already advertised by `GET /ui/settings-schema` and the documented `/ui/settings` contract), so updates apply and persist end-to-end, and `GET /ui/settings` includes them — which also activates the Angular settings page's pre-existing fields for these keys, previously filtered out because they were missing from the defaults response. The reference `database/schema.sql` seed was updated to stay identical to the app's self-seed. ## [4.14.1] — Silicon Falcon (2026-10-17)

- Made the graceful-shutdown HTTP step bounded so a slow in-flight request (or the Node 22 keep-alive idle drain that follows a response) can no longer consume the whole 15-second shutdown budget. Previously `closeHttpServer()` was a bare `server.close(cb)`, which only resolves once every connection is gone: an in-flight sensor command (up to the 10s command cap) plus the ~5s keep-alive drain could push the HTTP step past the 15s hard net on its own, so the safety net forced `process.exit(1)` and the MQTT, settings and logger cleanup was skipped — reporting a clean stop as a crash (exit 1) and dropping the final log flush. After a short grace (~4s) the server now calls `closeAllConnections()` to force-close in-flight and idle keep-alive connections, bounding the HTTP step so the remaining MQTT / settings / logger closes always get their time. In-flight HTTP requests are torn down after the grace instead of completing up to their own cap — acceptable at shutdown and consistent with the bounded-shutdown invariant. A new integration test sends SIGTERM with a request still in flight and asserts a clean exit 0 (it fails with exit 1 at the 15s net on the previous code).

## [4.14.0] — Silicon Falcon (2026-10-16)

- Added a central two-tier log redaction pass in the shared `Logger`: every log line now goes through a single auditable redaction before reaching any transport (console and Loki). The service's own secret values (`db-password`, `loki-url`) are masked by exact value, and recognized sensitive key/value pairs (`wifi-password`, `password`, `db-password`, `loki-url` in JSON-like form) are masked by key pattern — which also covers the previously unredacted untrusted forwarded-sensor-log path. Redaction used to be caller-driven at each log call site, so the INVARIANTS §2 credential-hygiene guarantee now holds structurally instead of resting on per-call-site discipline; existing caller-side redaction (`redactConfig`, `redactSecrets`, write-config metadata projection) is retained as defense in depth. Covered by 25 new tests, including a key-set drift guard and transport-capture integration tests.

## [4.13.16] — Graphite Falcon (2026-10-16)

- Hardened the settings store's key validation (defense in depth): `patchSettings` validated setting keys with prototype-chain membership (`in`), which accepts `__proto__`, `constructor`, and `prototype` as valid keys — writing one would rewrite the in-memory cache's prototype chain instead of a setting. Key validation now uses own-property membership (`Object.hasOwn`) and explicitly rejects the reserved keys in any dot-notation segment. The HTTP settings-update path was already safe end-to-end (global middleware strips these keys and the strict schema rejects unknown ones), so there is no externally visible behavior change — the guarantee now holds structurally in the settings layer instead of resting on middleware ordering alone. Regression tests pin the reserved-key rejection, including a prototype-pollution guard through `patchSettings` that fails against the old logic.

## [4.13.15] — Graphite Falcon (2026-10-16)

- Aligned the reference database schema (`database/schema.sql`) with the app's own settings defaults: its seeded telemetry display-mapping keys were stale kebab-case (`temperature-c`) while the app's defaults and the live sensor telemetry use snake_case (`temperature_c`), so an operator who ran the reference schema before first app start would have gotten display keys that never matched live sensor data.
